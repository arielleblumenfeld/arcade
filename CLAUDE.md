# Working agreement

This project is for Stanford MS&E 203. We're building a small browser game (blackjack, with a strategy coach you can switch on and off), saving it to GitHub, and deploying it to Vercel. The student is new to coding and wants to learn. They know GitHub a little and have never used Vercel.

## How we work

- **Small chunks.** For each chunk: say what we're about to do and why, do it, then show what changed and how the student can check it themselves.
- **Terms only when needed.** Introduce a term only when this project needs it.
- **Light checkpoints.** At useful checkpoints, ask one short question or have the student try something. Don't quiz after every command.
- **Pace.** "More detail" means slow down and explain more. "Move faster" means keep going with less explanation.

## Two rules

1. **Predictions.** When a prompt starts with "My prediction:" and the prediction is blank or vague, ask for a specific one before running anything. Never write the prediction for the student. At the end of that step, say in one line whether the prediction held.
2. **One step at a time.** If more than one step is pasted at once, do only the first.
